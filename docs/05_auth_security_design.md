# 05. 認証・セキュリティ設計

## 1. 認証方式

| 項目             | 内容                              |
| ---------------- | --------------------------------- |
| ログインID       | メールアドレス                    |
| パスワード保存   | bcrypt hash。salt roundsは12      |
| セッション方式   | JWT                               |
| トークン有効期限 | `JWT_EXPIRES_IN`。デフォルト `7d` |
| 署名鍵           | `JWT_SECRET`                      |
| API認証          | `Authorization: Bearer <token>`   |

## 3. JWTペイロード

JWTには以下の認証コンテキストを含める。

| 項目     | 内容                        |
| -------- | --------------------------- |
| `userId` | ユーザーID                  |
| `role`   | `freelancer` または `sales` |
| `email`  | メールアドレス              |
| `iat`    | 発行時刻                    |
| `exp`    | 期限                        |

APIはJWT検証後、DB上のユーザー存在と `isActive` を確認する。

## 4. 個人情報暗号化

### 4.1 暗号方式

| 項目         | 内容                                       |
| ------------ | ------------------------------------------ |
| アルゴリズム | AES-256-GCM                                |
| IV           | 12 bytes random                            |
| 認証タグ     | 16 bytes                                   |
| 保存形式     | `enc:v1:<base64(iv + tag + encrypted)>`    |
| 鍵           | `DATA_ENCRYPTION_KEY`。Base64 32 bytes推奨 |

`DATA_ENCRYPTION_KEY` が未設定の場合、ローカル開発用の固定文字列からSHA-256で鍵を生成する。本番環境では必ず環境ごとに固定した安全な鍵を設定する必要がある。

### 4.2 ハッシュ方式

検索や一意制約が必要な個人情報にはHMAC-SHA256を使用する。

| 対象           | ハッシュ列                         | 目的                   |
| -------------- | ---------------------------------- | ---------------------- |
| メールアドレス | `users.email_hash`                 | ログイン検索、重複防止 |
| Push endpoint  | `push_subscriptions.endpoint_hash` | 購読重複防止、削除検索 |

## 5. CORS

- `CORS_ORIGIN` に設定されたオリジンのみ許可する。
- デフォルトは `http://127.0.0.1:5173,http://localhost:5173`。
- 許可外オリジンは `403 CORS_FORBIDDEN`。

## 6. 入力バリデーション

Zod schemaによりAPIごとに入力を検証する。

| API               | 主な検証                                                       |
| ----------------- | -------------------------------------------------------------- |
| register          | メール形式、パスワード8〜128文字、プライバシーポリシー同意必須 |
| create job        | 案件名必須、単価0以上、最大単価 >= 最小単価、マージン率0〜100  |
| update profile    | 経験年数0〜99、各文字列長、enum値                              |
| meeting           | `candidateAt` はoffset付きdatetime                             |
| message           | 本文必須                                                       |
| push subscription | endpointはURL形式                                              |

## 7. エラーハンドリング

アプリケーションエラーは `AppError` としてHTTPステータス、メッセージ、コードを保持する。Prisma既知エラーも共通形式に変換する。

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "入力内容を確認してください。"
  }
}
```

## 8. セキュリティ上の注意点

| 項目                 | 現状                      | 推奨                                                      |
| -------------------- | ------------------------- | --------------------------------------------------------- |
| JWT保存              | フロント側でトークン保持  | XSS対策を徹底。必要に応じてHttpOnly Cookie化を検討        |
| API_BASE             | フロントに固定値          | 環境変数化を推奨                                          |
| レジュメ             | メタ情報のみDB保存        | ファイル本体の保存先、署名URL、ウイルススキャン方針を定義 |
| read_at              | カラムはあるが更新APIなし | 既読管理が必要ならAPI追加                                 |
| 監査ログ             | 応募ステータス履歴は保存  | 管理操作全般の監査ログ追加を検討                          |
| レート制限           | 実装なし                  | ログイン/APIにrate limit導入を推奨                        |
| CSRF                 | Bearer Token前提          | Cookie認証化する場合はCSRF対策が必要                      |
| セキュリティヘッダー | 明示実装なし              | helmet等の導入を検討                                      |
